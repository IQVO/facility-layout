# How to add a frontend remote

Use when adding a new screen/feature to `web/` (the `facility-mfe` Module
Federation remote), or as the reference shape for standing up a NEW
remote for a bounded context that doesn't have one yet. This is the
Vite/React micro-frontend layer that `warehouse-console` (the shell)
lazy-loads.

## `vite.config.ts` must stay in OBJECT form, always

This repo's own `web/vite.config.ts` states the rule in its own comment
and gives the exact working shape:

```ts
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/facility-layout/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  plugins: [
    react(),
    federation({
      name: "facility_mfe",
      filename: "remoteEntry.js",
      exposes: { "./App": "./src/App.tsx" },
      shared: {
        react: { singleton: true, requiredVersion: "^19.2.8" },
        "react-dom": { singleton: true, requiredVersion: "^19.2.8" },
        "react-router-dom": { singleton: true, requiredVersion: "^7.18.3" },
        "@warehouse/ui-kit": { singleton: true },
      },
    }),
  ],
  // ...
});
```

Never convert this to the callback form
(`defineConfig(({ command }) => ({...}))`) to compute `base`
dynamically. `web/vitest.config.ts` does `mergeConfig(viteConfig,
defineConfig({...}))`, and Vite throws `Error: Cannot merge config in
form of callback` on a function export — killing the ENTIRE test suite
for a one-line config change, not just a new test. Reading the command
off `process.argv` (as above) keeps `vite.config.ts` a static object
while still knowing whether it's a `build` invocation.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After a build with the `/mfes/facility-layout/` base, `dist/remoteEntry.js`
is a small relative re-export — grepping it for `/mfes/facility-layout/`
returns zero matches. That is expected, not a bug: `dist/index.html`
carries the absolute prefixed URLs, every JS chunk uses relative ESM
imports, and the module-preload helper resolves relative to wherever
`remoteEntry.js` was actually fetched from — exactly what a path-mounted
remote needs. Verify correctness by serving the built image and fetching
through the real gateway path (`http://localhost/mfes/facility-layout/`
per the Nginx web gateway split — see this repo's `web/vite.config.ts`
comment), never by grepping the built file for the expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`web/package.json` depends on it via `"@warehouse/ui-kit":
"file:../../warehouse-ui-kit"`. Any domain-status color, chart, or
shared layout primitive belongs in that repo, not hand-rolled here — a
remote reinventing its own palette instead of consuming the shared
components is a bug, not a style choice.

## Give the remote a `test` script, or added tests silently never run

Confirmed already correct in this repo (not a gap to fix, but the check
to make on any NEW remote): `web/package.json`'s `scripts.test` is
`"vitest run"`. Several other remotes in this fleet historically shipped
`package.json` with only build/dev/lint/preview — `npm test` failed with
`Missing script: "test"`, and any `.test.ts` file added there silently
never executed. This repo's own `web:` CI job
(`.github/workflows/ci.yml`) does invoke `npm test` as a distinct step
from `npm run build` — verify a NEW remote's job does the same rather
than assuming a passing build implies tests ran.

## The Docker build recipe (packaging as a deployable nginx workload)

This repo's `web/Dockerfile` is the complete, working, heavily-commented
reference — copy it rather than re-deriving these traps from scratch for
a new remote. Three traps, in the order its own comments explain them:

1. **Base image must be `node:22-bookworm-slim`, not alpine or a newer
   node image.** `web/package-lock.json` was generated by npm 10 on
   macOS and carries no linux entries for Vite 8's platform-specific
   optional dependencies (`@rolldown/binding-linux-*`,
   `lightningcss-linux-*`, `@oxlint/binding-linux-*`). npm 11 (shipped
   with newer node images) rejects that lockfile outright with `EUSAGE
   "lock file out of sync"`; Debian/glibc matches the published `*-gnu`
   bindings that alpine's musl does not.
2. **Do NOT install from the committed lockfile, and do NOT reuse a
   host `node_modules`.** Both leave the native binding missing
   (`Cannot find native binding ... @rolldown/binding-linux-*`, a known
   npm/cli optional-dependency bug, npm/cli#4828). The working recipe,
   straight from `web/Dockerfile`'s uikit-build stage: `rm -rf
   node_modules package-lock.json && npm install --no-save && npm run
   build`, and for the remote's own build stage: `COPY package.json
   ./` only, `npm install --no-save`, then `COPY . .` followed by
   `rm -f package-lock.json` before `npm run build`.
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**,
   since it's a sibling checkout, not a registry dependency:
   ```bash
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/facility-layout-frontend:local .
   ```

The runtime stage is `nginxinc/nginx-unprivileged:1.31-alpine` with an
`apk upgrade --no-cache` as root before switching back to the `nginx`
user — done specifically to pick up CVE fixes published to the alpine
branch since the base image was last rebuilt; keep that step when
copying this Dockerfile for a new remote.

## Wiring into the deploy

A new remote isn't deployed automatically. This repo's own Helm chart
(`charts/facility-layout/values.yaml`, the `frontend:` block starting at
line 224) is gated by `frontend.enabled` (default `false`) with a
comment explaining the deliberate omission: "Deliberately NO
ingress/httproute/gatewayApi block here: frontend path routing is owned
entirely by the Nginx web gateway, and the Service stays ClusterIP so
this is not a second host-facing entrypoint," and separately: "Disabled
by default so existing releases are unaffected; warehouse-infra sets
frontend.enabled=true and supplies the locally built image tag."
`warehouse-infra`'s Terraform `local.services` map is the separate thing
that has to know about this repo's frontend before anything actually
deploys it — see that repo's own docs for the Terraform side; this repo
only needs to ship a working chart with that toggle.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint
npx tsc -b           # typecheck
npm test             # vitest run — confirm this actually runs your new test
npm run build         # tsc -b && vite build -> dist/
```

CI's `web:` job (`.github/workflows/ci.yml`) runs this exact sequence
against a DUAL checkout — this repo's `web/` plus a fresh clone of
`claudioed/warehouse-ui-kit@develop` built first and copied in as
`file:../../warehouse-ui-kit` would expect. Reproduce that locally by
checking out `warehouse-ui-kit` as a real sibling directory (`../
warehouse-ui-kit` relative to this repo) if `npm ci` behaves differently
locally than in CI.
